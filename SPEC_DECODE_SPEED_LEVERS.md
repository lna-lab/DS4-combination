Source: scoping workflow wf_c07daa9b-ad0 (2026-06-16). Empirical floor = per-layer host-driven
expert gather (cudaStreamSynchronize+D2H selected+host LRU scans+D2D compact copies, x43 layers).
GPU-LRU already took 6.1->8.65. Honest ceiling on TP=2/32GB: ~16-18 expected, 20 = stretch.

## Lever 1: GPU-resident expert→slot resolution: make the MoE decode kernels index the persistent LRU buffers directly via a device-side `expert_id→slot` table, so a cache HIT does zero host work (no cudaStreamSynchronize, no D2H of selected ids, no host LRU scan, no D2D compact copy). Host involvement shrinks to a once-per-layer miss-list readback that only fires on the residual 1-2 misses/layer.

**Effort:** large  **Verdict:** GO — this is the only lever that attacks the structural per-layer host round-trip floor the prompt identifies; the kernel weight-base math is already slot-indexed so the change is mostly plumbing + a 30-line resolve kernel, and it sets up the same win for the permanently-streaming Pro 1.6T.

**Design:**
CURRENT FLOOR (verified):
- routed_moe_launch streaming branch, ds4_cuda.cu:14368-14406: per layer it does cudaStreamSynchronize(decode_stream) (14375), cudaMemcpy D2H of selected ids (14378), then ds4_gpu_stream_expert_cache_prepare_selected_batch (14398).
- prepare_selected_batch (4634-4659) builds expert_to_slot[n_total_expert=256] + compact_ids on host, then begin_compact_load (4400-4503) runs the host LRU: cuda_stream_expert_cache_find (2387, O(capacity≈748) linear scan) and _lru_slot (2419, another O(capacity) scan) PER compact expert, then cuda_stream_expert_cache_copy_to_compact (2435) issues 3 D2D memcpys per expert into g_stream_selected_cache[dev].{gate,up,down}_ptr, then cudaMemcpy H2D of the slot map (4505).
- Kernel moe_gate_up_mid_decode_lut_qwarp32_kernel (12593): expert_i = selected[tok*n_expert+slot] (12614); weight base = gate_base + expert_i*gate_expert_bytes (12631-12632). In streaming mode gate_base = g_stream_selected_cache[dev].gate_ptr (the compact copy) and selected = slot_selected_ptr (host-built compact slot index).

NEW DESIGN — read experts in place from the LRU, resolve slot on GPU.

(1) Persistent device slot directory. Add to cuda_stream_expert_cache (struct at 635): `int32_t *d_expert_slot[n_layers]` OR a single flat `int32_t *d_layer_expert_slot` sized n_layers*n_total_expert, allocated once per device (43*256*4 = 44KB, trivial). Entry = LRU slot index holding (layer,expert), or -1. Maintain it as the mirror of the host slots[] vector: every cuda_stream_expert_cache_load_slot (2469) and the eviction in _lru_slot already know (old_layer,old_expert)->slot and (new_layer,new_expert)->slot; on each load, set d_layer_expert_slot[evicted]= -1 and d_layer_expert_slot[loaded]=slot via a tiny 2-int cudaMemcpyAsync (or a 1-thread kernel) on the decode stream. This keeps the directory authoritative without any per-token rebuild.

(2) GPU resolve kernel (new, ~30 lines, near 12593). Inputs: the RAW router-selected expert ids that are ALREADY on device (selected->ptr, the same buffer line 14378 copies to host), the d_layer_expert_slot row for this layer, n_selected*n_tokens. Output: int32_t *d_resolved_slot[18] (the LRU slot per pair) AND an atomically-built int32_t miss list + miss count (d_miss_ids[≤18], d_miss_count). One block, 18 threads:
    int e = selected[i]; int s = dir[e];
    resolved[i] = s;                       // -1 if miss
    if (s < 0) miss_ids[atomicAdd(d_miss_count,1)] = e;
Launch on decode stream. No host sync.

(3) Kernel reads LRU directly. Change the streaming branch so gate_w/up_w/down_w point at g_stream_expert_cache[dev].{gate,up,down}_ptr (the persistent LRU, NOT the compact copy), and selected_ptr (14487) points at d_resolved_slot. Because the kernel already computes base + expert_i*expert_bytes (12631), and the LRU buffer is laid out as slot*expert_bytes (load_slot dst at 2488), feeding it the LRU slot index makes it read the right bytes with ZERO code change to the math — only the base pointer and the index array change. Do the same substitution at the moe_down kernel call (14826) and its base.

(4) Miss handling (residual 1-2/layer). Two options, both keep the common case host-free:
  (a) READBACK-ONCE (recommended, deterministic-safe): after the resolve kernel, do ONE cudaMemcpyAsync D2H of d_miss_count+d_miss_ids (≤76 bytes) and a single cudaStreamSynchronize. If miss_count==0 (the 4-6/6-hit common case) you paid one tiny async copy + one sync but NO 256-wide rebuild, NO O(748) host scans, NO 3-D2D-per-expert. If miss_count>0, host issues exactly miss_count expert loads via cuda_stream_expert_cache_load_slot (2469) into freshly LRU-evicted slots, updates host slots[] + the device directory (step 1), then re-launches the resolve kernel (now all hits) before the MoE kernels. This replaces ~258 host find-scans/token with ~12-24 (only on the ~1-2 actual misses).
  (b) ACCEPT-STALE + ASYNC BACKFILL (max-throughput, lossy): on a miss, resolved[i] stays -1; kernel treats expert=0 (it already clamps expert_i<0 to 0 at 12615) OR better, skip its contribution. Meanwhile the resolve kernel's miss list is drained by a host backfill that loads the missing experts for the NEXT token. With 4-6/6 steady-state hits this perturbs ≤2 experts/layer; quality impact must be measured. Keep behind an env flag DS4_STREAM_STALE_OK; default to (a).

(5) Eliminate the compact copy + compact buffers entirely in the streaming hit path. Since the kernel now reads the LRU in place, g_stream_selected_cache compact gate/up/down (596-617) and cuda_stream_expert_cache_copy_to_compact (2435, the 3 D2D/expert) are no longer used in streaming decode — delete the copy_to_compact calls (4460-4473) from the hit path. This also frees the ~compact_count*expert_bytes VRAM, letting cuda_stream_expert_cache_live_budget (1944) raise the LRU capacity above 748 → fewer misses → compounding win.

(6) Graph capture: NOT needed and explicitly avoided. ds4_gpu_decode_graph_can_capture already returns 0 under g_ssd_streaming_mode (noted at 14354-14356). The resolve kernel + the optional single miss-sync run outside capture on the decode stream exactly like today's path; the existing capture fallback at 14351-14367 (which points at prior-pass buffers) can keep pointing at the LRU buffers since they are persistent. No graph work.

(7) Correctness anchors: (i) the directory must be invalidated wherever the LRU is — hook cuda_stream_expert_cache_invalidate (1873) and _release_all to memset the directory to -1. (ii) The (layer,expert)->slot identity in find() (2402-2412) also checks model_map/offsets; the directory key is (layer,expert) which is sufficient as long as model_map is constant within a run (it is; one mmap). Guard by storing model_map once and asserting. (iii) MTP batch (n_tokens up to 3, 18 pairs) already handled: resolve kernel loops over slot_count=n_tokens*n_expert exactly like the host loop at 4640.

ORDER OF WORK: directory struct+alloc+invalidate (step1) → resolve kernel (step2) → wire base+index swap behind a DS4_STREAM_GPU_GATHER env flag, keeping the old host path as fallback (step3+5) → readback-once miss path (step4a) → measure → then raise LRU cap (step5 freed VRAM) → optionally stale mode (4b).

**Expected gain:** The host floor today is: per layer 1 cudaStreamSynchronize + 1 D2H + a 256-wide expert_to_slot rebuild + ~6 host LRU find scans (O(748) each ≈ 4.5K compares) + ~18 D2D compact copies; ×43 layers/token. The prompt attributes the 8.7 t/s ceiling to exactly this ping-pong, and states the no-host resident path already reaches 19-21 t/s. The GPU-gather hit path removes everything except, in option (a), one ~76-byte async copy + one stream sync per layer (a sync is ~5-15us vs the multi-ms host LRU/compact work). Realistic landing: 14-18 t/s. Reasoning: we do NOT fully reach the 19-21 resident number because (i) we still issue a per-layer sync for the miss readback (option a), and (ii) the residual 1-2 misses/layer still cost synchronous PCIe H2D (the irreducible ~110ms/token copy headroom the prompt cites is only partly removed — gather removes bookkeeping, not the misses themselves). Eliminating the compact D2D copies + the freed-VRAM LRU cap bump (>748) is the compounding lever that pushes toward the top of that range and cuts the miss rate. Going to option (b) stale could approach ~19 if quality holds. Honest point estimate toward the 20 t/s goal: +6 to +9 t/s (8.7 → ~15-18); the last few t/s to 20 need the LRU-cap increase from freed VRAM and/or MTP, not gather alone.

**Risks:** Miss readback still needs one cudaStreamSynchronize/layer (option a); if the kernel launch + tiny copy latency dominates, gain is capped below estimate — measure the sync cost before assuming 15-18.; Device directory coherence: any path that loads/evicts LRU slots without updating d_layer_expert_slot silently feeds the kernel a wrong slot → reads the wrong expert bytes (garbage logits). Every load_slot/evict/invalidate/release site (2469, 2419, 1873, 4204) must update the directory; easy to miss one. Gate behind an env flag and diff logits vs the host path on a fixed seed.; VRAM: directory is tiny, but reading the LRU in place means the LRU buffer must hold ALL distinct experts referenced THIS layer simultaneously (it already does — they were loaded as hits), AND the kernel reads scattered slots (non-contiguous) vs today's contiguous compact buffer — slightly worse L2/coalescing across experts, though each expert's rows are still contiguous so likely negligible.; Accept-stale (4b) can change outputs; DeepSeek routing is sensitive — must A/B perplexity, keep default off.; MTP batch path shares the same buffers; the 18-pair resolve must match prepare_selected_batch's slot_count semantics (n_tokens*n_expert) exactly or MTP verify breaks.; Determinism: Ken's models are run deterministically (Tokyo bring-up); the atomicAdd miss-list ordering is non-deterministic but only affects WHICH slot a miss loads into, not the computed value, so logits stay deterministic — verify this holds.

**Effort:** small  **Verdict:** GO (small effort, high confidence it builds & runs) — download the 3.8GB MTP GGUF, run with --mtp FILE --mtp-draft 2 greedy, measure accept rate via the probe counter; expect ~12 t/s, a real ~1.4x but NOT the path to 20 on its own.

**Design:**
FINDINGS:

(3) GATHER AMORTIZES (the key question). The batch MoE ds4_gpu_routed_moe_batch_tensor (ds4_cuda.cu:15031) in streaming mode (ds4_cuda.cu:14381) calls ds4_gpu_stream_expert_cache_prepare_selected_batch (ds4_cuda.cu:4610) with slot_count = n_tokens*n_selected. It builds compact_ids = the SET of DISTINCT experts across all N rows (dedup loop ds4_cuda.cu:4634-4659), then the copy loop (ds4_cuda.cu:4400-4503) iterates compact_count and for each distinct expert checks the per-device GPU-LRU (cuda_stream_expert_cache_find) — only LRU MISSES do the PCIe H2D copy. So a verify of N rows costs (distinct experts across N rows) - (LRU hits), NOT N*6 copies. Two adjacent positions share the shared expert + heavily-overlapping routed experts, and the cache is already warm from the prior committed token, so the MARGINAL new misses for row 2 are small (~+0.3-0.7 miss/layer over the single-token baseline). The gather amortizes; it does not multiply.

**Expected gain:** +3.5 to +4 t/s (8.65 -> ~12 t/s), NOT to 20. Math: per-token ~115 ms; the verify pass is ~1.0-1.4x a single token (same warm-LRU gather + a few extra distinct-expert misses for the 2nd row + 2-row compute which is near-free since decode is transfer-bound). MTP first-token accept ~0.8-0.85 in-distribution => effective ~1.8 tokens per verify-step at cost ~1.27 token-equiv (incl ~0.07 draft) => ~1.42x => ~12.3 t/s. N=2 is the sweet spot: N=4 makes the batch dedup pull in ~14-18 distinct experts/layer (more marginal misses, verify ~1.5-1.8x a token) while chained acceptance decays to ~2.4 expected tokens => only ~1.26x (~11 t/s), WORSE than N=2. The streaming/PCIe-bound regime fundamentally caps MTP below the ~1.8x it would give in a compute-bound engine, because each extra verify row is not free — it adds gather misses. Honest verdict: MTP is a real but partial win (~1.4x), it does NOT close the gap to 20 t/s alone. Stacks multiplicatively with any future LRU/host-ping-pong fix.

**Risks:** Greedy-only: spec path is gated on temperature<=0 (ds4_cli.c:556 etc). Sampled generation gets no MTP speedup — fine for deterministic bench, a limit for creative serving.; Batch-verify greedy-divergence: non-quality N=2 batch verifier may pick a different argmax than serial decode on near-tied logits (ds4.c:20536 comment); --quality/DS4_MTP_STRICT forces the exact decode2 verifier which is correctness-safe but the comment warns it is 'not a speed win' — must bench strict-vs-batch to confirm the 1.4x holds under strict.; Accept rate is an estimate: DeepSeek MTP ~0.8-0.85 is from upstream/in-distribution; IQ2 quant of BOTH target and the Q4K MTP head could lower agreement (every quant mismatch flips a draft). Real accept rate must be measured (DS4_MTP_PROBE / mtp_probe_hit counter, ds4.c:20316) before trusting the gain.; +3.8 GB resident VRAM for the MTP block competes with the 748-expert LRU cap (only ~5.93 GiB free/card) — the MTP weights live where LRU experts would; could DROP cache hits and partially self-defeat. Must verify the MTP block is placed off the streaming devices or its VRAM cost is accounted against LRU capacity.; N=2 batch path reuses prefill/batch kernels (verify_suffix_tops comment ds4.c:15452 'not yet the final hand-written N=2 decode microbatch') — extra per-row overhead may make real verify cost closer to 1.4x than 1.0x, pulling net toward ~11.5 t/s.; CUDA decode-graph capture is a separate broken feature (crashes pos=19); ensure MTP path runs with graph capture OFF (do not enable it to 'help').

## Lever 3: Smaller streaming-decode levers: (1) async/overlapped miss loads (pinned-stage H2D), (2) O(1) hash map for LRU find()/lru_slot(), (3) other quick per-layer host-cost shaves — for Flash TP=2 streaming 8.65 -> 20 t/s.

**Effort:** medium  **Verdict:** MAYBE — Lever 1 (async pinned miss loads) is the only one worth building now for ~+1-2 t/s; Levers 2/3a/3b are ~free correctness/plumbing to bundle but ~0 measurable on their own. None reach 20 t/s without the unscoped GPU-side gather (3c) + scratch-freeing; scope these as the enabling stack, not the unlock.

**Design:**
CRITICAL-PATH MAP (decode, n_tokens==1, n_expert==6), per layer x43/token, all in ds4_cuda.cu routed_moe_launch:
- 14375 cudaStreamSynchronize(decode_stream) [blocks host on router kernel]
- 14378 cudaMemcpy(host_selected, DeviceToHost) [24B, sync]
- 14398 -> ds4_gpu_stream_expert_cache_prepare_selected_batch (4610): builds expert_to_slot/compact_ids/slot_ids in fresh std::vectors (heap alloc/layer)
- 4400-4503 begin_compact_load loop over <=6 unique experts: cuda_stream_expert_cache_find (2387, O(748) x ~11 field-compares), on hit -> 3x cudaMemcpyAsync D2D (2435, already async, gather); on miss -> cuda_stream_expert_cache_lru_slot (2419, O(748)) + cuda_stream_expert_cache_load_slot (2469) -> 3x cuda_model_copy_to_device_streamed (2610) SYNCHRONOUS pageable cudaMemcpy H2D (2641)
- 4505 cudaMemcpy(slot_selected_ptr, H2D) [<=24B, sync]
- then MoE kernels enqueued on decode stream.

LEVER (1) ASYNC MISS LOADS — design: in cuda_stream_expert_cache_load_slot, replace the 3 synchronous mmap->H2D copies (gate/up/down for a miss) with: memcpy mmap->pinned staging (g_stream_selected_stage pool already allocated, 2186 cudaMallocHost) then cudaMemcpyAsync(pinned->VRAM, decode_stream). All misses in a layer issued before any sync; the slot-map upload at 4505 + the MoE kernel on the same stream naturally orders after them, so NO explicit per-miss sync needed (collapses N per-miss syncs -> 0; the existing 4505 H2D already serializes). HONEST ASSESSMENT: this does NOT overlap with compute on the critical path — the MoE kernel for THIS layer must wait for THIS layer's miss bytes to land (misses block the layer; the gather feeds the immediately-following kernel). What it removes is: (a) the implicit per-miss host stall of synchronous pageable cudaMemcpy (driver staging through a small internal pinned buffer, ~serialized), replaced by one DMA from a large pinned buffer at full PCIe; (b) lets the 2-6 miss copies of a layer pipeline against each other on the copy engine instead of host-serialized. The pinned memcpy (mmap page-cache -> pinned) is itself a CPU cost (~6.75MiB x ~1.5 misses x43 ~ 435MiB/token of CPU memcpy ~ a few ms). Net win is bandwidth/serialization on misses only (the ~1-2/layer residual), not the hit path.

LEVER (2) O(1) HASH MAP — design: add std::unordered_map<uint64_t,uint32_t> (key = pack(layer,expert) since model_map/offsets/bytes are constant within a run) to cuda_stream_expert_cache, maintained on insert/evict in load_slot/lru_slot; replace find() linear scan (2400) with map.find. lru_slot O(748) eviction scan stays unless you also add an intrusive LRU doubly-linked list / min-age heap. HONEST ASSESSMENT: marginal. find runs <=6x/layer over capacity 748 x ~11 compares = ~2.1M cmp/token ~ <2ms of a ~115ms token (<2%). lru_slot runs only on the ~1-2 misses/layer. Pure-CPU, fully hidden behind the GPU/PCIe wall.

LEVER (3) OTHER QUICK WINS:
- 3a: hoist the per-layer std::vector allocations in prepare_selected_batch (4634-4637 expert_to_slot/compact_ids/slot_ids) to reused thread-static/static buffers sized to n_total_expert/slot_count. Removes ~3 heap alloc+free/layer x43/token. Sub-ms; trivial.
- 3b: the slot-map H2D at 4505 and host_selected D2H at 14378 are tiny (<=24B) but each is a synchronous round-trip; merge by leaving slot_selected on a persistent pinned buffer and using cudaMemcpyAsync on decode_stream (kernel orders after). Removes 1 sync/layer. Small.
- 3c (NOT in scope but the actual unlock, per memory): GPU-side gather — keep router selected on GPU, a small kernel resolves expert->LRU-slot from a device-resident slot table, MoE kernel reads LRU directly; host touched only to service misses. This removes the 14375 cudaStreamSynchronize + 14378 D2H entirely (the real per-layer floor). The three scoped levers do NOT remove that floor.

**Expected gain:** Anchored to measured ~115ms/token at 8.65 t/s, 43 layers, ~1-2 misses/layer.
- Lever 1 (async/pinned miss loads): the ~1-2 misses/layer x43 = ~50-85 sync pageable H2D/token. Pageable cudaMemcpy stages through driver's small pinned buffer and stalls host per call; pinned-staged async lets the copy engine run the 2-6 miss copies of a layer back-to-back at full PCIe and removes host-stall serialization. Realistic: shaves maybe 10-25ms/token -> ~9.5-10.5 t/s. Offset by the new CPU mmap->pinned memcpy cost (~few ms). NET +0.8-1.8 t/s. Memory already records 'async copy_to_compact (D2D gather): no gain' — that was the HIT path; this is the MISS path, which is the real residual, so a small-but-real gain is plausible but not large.
- Lever 2 (hash map): <2ms/token CPU, fully hidden behind GPU/PCIe. NET ~0 t/s measurable. Do it only for Pro-1.6T where capacity may be larger and miss rate higher, or fold into Lever 3c's device table.
- Lever 3a/3b: sub-ms each, NET ~0-0.3 t/s.
TOTAL realistic from all three scoped levers: ~8.65 -> ~9.5-11 t/s (+1-2.5 t/s). This does NOT reach 20. The 20 t/s target requires (i) freeing the 1.7GB transient scratch to grow the cache (raises hit rate -> fewer misses, multiplies Lever 1) AND (ii) Lever 3c GPU-side gather to kill the per-layer cudaStreamSynchronize+D2H floor. The three small levers are necessary plumbing but not sufficient alone.

**Risks:** Lever 1: cudaMemcpyAsync from pinned is async, but the mmap->pinned CPU memcpy adds host work that may eat most of the PCIe-serialization saving; must benchmark, easy to net-zero.; Lever 1: must keep the existing pread/DS4_CUDA_STREAM_USE_PREAD staging path (2648+) distinct — the default mmap path (2641) is the one to convert; do not regress the proven byte-identical mmap correctness.; Lever 1: ordering correctness — if miss copies go on decode_stream they order before the MoE kernel automatically, but D2D hit gathers (copy_to_compact, 2451) ALSO read just-loaded slots; a miss load must complete before its copy_to_compact reads it. In the current code load happens then copy_to_compact on same stream = safe; keep that ordering when batching.; Lever 2: unordered_map insert/erase per miss can allocate; use a fixed open-addressing table sized to capacity to avoid heap churn, else it costs more than the scan it replaces.; Lever 3a: static/thread-local reuse buffers must be sized for the largest n_total_expert across target+MTP models (same multi-model aliasing concern as g_moe_compact_* at 14307).; Headroom risk: profiling already proved the per-layer cudaStreamSynchronize+D2H is the floor; these levers leave it intact, so gains cap well below 20 t/s — do not oversell to Ken.

## RANKED PLAN

This is an architecture decision task — I have all three lever scopes with verified profiling data. No file reading needed; I'll synthesize the ranked plan directly.

RANKED GO/NO-GO PLAN — Flash TP=2 streaming decode 8.7 → 20 t/s

THE BOTTOM LINE FIRST
20 t/s is NOT reachable on TP=2/32GB with gather+MTP alone. Realistic ceiling on TP=2 is ~15-18 t/s. To actually hit 20 you need the VRAM-cap bump (freed by deleting the compact buffers) AND MTP stacked on top of gather — and even then 20 is the optimistic edge, not the expected value. State this to Ken plainly; do not promise 20 from any single lever.

THE REAL UNLOCK (single lever)
Lever 1 — GPU-resident expert→slot resolution (device directory + 30-line resolve kernel, reads LRU in place). This is the ONLY lever that attacks the structural floor the profiling identified: the per-layer cudaStreamSynchronize + D2H + host LRU scans + D2D compact copies, ×43 layers/token. Everything else is either a fraction of this or multiplies on top of it. The kernel weight-base math is already slot-indexed (base + expert_i*expert_bytes), so this is mostly plumbing plus one small kernel — high leverage for "large" effort. GO, build first.

RANKING by (gain toward 20)/(effort)

1. Lever 1 — GPU-side gather. GO. Effort large, gain +6 to +9 (8.7 → ~15-17). Highest absolute gain and the only structural fix. Note: step (5) — deleting copy_to_compact and its compact gate/up/down buffers — is not optional polish; it frees VRAM that raises the LRU cap above 748, which cuts the miss rate, which compounds every other lever. Treat step 5 as part of Lever 1, not a follow-on.

2. Lever 2 — MTP N=2 spec decode. GO. Effort small, gain ~1.4× (≈ +3.5-4). Best effort-adjusted ratio of all three. Caveats that are real: greedy-only; +3.8 GB resident competes with the LRU cap (must place the MTP block on a non-streaming device or account its VRAM against capacity — otherwise it self-defeats by dropping cache hits); accept rate is an ESTIMATE (IQ2 target × Q4K draft mismatch) and must be measured via the probe counter before trusting the number. Stacks multiplicatively with Lever 1 — this is what pushes the gather's ~15-17 toward ~18-20.

3. Lever 3.1 — async pinned miss loads. CONDITIONAL GO, but only AFTER Lever 1. Effort medium, gain +0.8-1.8 on its own. Important re-scoping: once Lever 1 raises the LRU cap and cuts the miss rate, this lever's headroom shrinks — but it directly attacks the residual that Lever 1 explicitly does NOT remove (the irreducible synchronous PCIe H2D on the 1-2 real misses/layer). So its value is highest as the LAST shave, on top of gather, where misses are the only remaining host stall. Build it third.

DROP / DEFER
